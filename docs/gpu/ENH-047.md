## 2. Arguments (v1)

```
enhance-bench --stage decode    --in <vidéo>  [--report <json>] [--repeat N] [--warmup K] [--max-frames M]
                                              [--decoder auto|nvdec|software] [--sample-ms T]
enhance-bench --stage vsr-image --in <image.bmp> --out <image.bmp> [--q 0..4] [--bits 8|10]
                                              [--size 3840x2160] [--iterations N] [--warmup K] [--report <json>] [--sample-ms T]
```

| Argument | Défaut | Rôle |
|---|---|---|
| `--stage` | (obligatoire) | `decode` ou `vsr-image` ; d'autres étages viendront (ENH-010 : `--codec --preset --bits` ; ENH-012 : `--interp`) |
| `--in` / `--out` | — | chemins ouverts comme dans l'application (`\\?\`, ENH-008) |
| `--report` | sortie standard | fichier JSON (créé en `CREATE_NEW` ; refus si existant, sauf `--force`) |
| `--repeat N` | 1 | le fichier est décodé N fois dans le même processus : sert à la mesure de fuite (« 10 fichiers à la suite ») |
| `--warmup K` | 30 (decode) / 30 (vsr) | images exclues du chronométrage (comme au spike) |
| `--max-frames M` | tout | limite le nombre d'images décodées |
| `--decoder` | `auto` | `software` force le repli (mesure ~1 300 i/s) ; `nvdec` échoue au lieu de se replier |
| `--q` | 4 | niveau `NVSDK_NGX_VSR_QualityLevel` (0 bicubique … 4 Ultra) |
| `--bits` | 8 | 10 : l'image 8 bits est convertie en ABGR10 avant la SR (mesure du chemin 10 bits) ; la sortie BMP reste 8 bits |
| `--size` | 3840x2160 | taille de sortie ; rapport d'aspect conservé dans ce cadre |
| `--iterations N` | 300 | nombre d'appels VSR chronométrés sur la même image |
| `--sample-ms T` | 10 | période d'échantillonnage de la VRAM |

Codes de sortie (`exit_code` du JSON) : `0` succès, `1` arguments invalides, `2` entrée illisible ou format non pris en charge, `3` GPU / pilote / composant absent, `4` VRAM insuffisante, `5` erreur interne. Un JSON est écrit même en cas d'échec (si `--report` a pu être ouvert), avec `error`.

## 3. Schéma du JSON (v1)

Champs exigés par le protocole QA § 4.3 (noms identiques), plus des champs de contexte :

```json
{
  "schema_version": 1,
  "tool": "enhance-bench", "tool_version": "0.1.0", "git_sha": "abcdef1",
  "gpu": "NVIDIA GeForce RTX 5070", "driver_version": "617.42", "cuda_driver_api": 13040,
  "stage": "decode",
  "input": { "name": "BBB-FAST.mp4", "size_bytes": 12345678, "codec": "h264", "width": 1280, "height": 720, "pix_fmt": "nv12" },
  "params": { "repeat": 1, "warmup": 30, "decoder": "auto", "q": null, "bits": null },
  "decoder_path": "nvdec",
  "frames_in": 1800, "frames_out": 1800,
  "wall_s": 0.61, "fps_out": 2950.8,
  "stages": [ { "name": "decode", "ms_total": 610.2, "ms_per_frame": 0.339 } ],
  "vram_process_start_mib": 0,
  "vram_context_mib": 141,
  "vram_rest_mib": 141,
  "vram_peak_mib": 302,
  "vram_stage_mib": 161,
  "vram_device_used_peak_mib": 2410,
  "vram_drift_mib": 0,
  "repeats": [ { "fps_out": 2950.8, "vram_peak_mib": 302, "vram_after_mib": 141 } ],
  "process_private_mib": { "start": 18, "end": 25 },
  "sample_period_ms": 10,
  "exit_code": 0,
  "error": null
}
```

Définitions :
- `frames_in` / `frames_out` : images décodées (decode) ou appels VSR (vsr-image), chauffe exclue. `wall_s` : durée murale chronométrée (`std::chrono::steady_clock`), après une synchronisation finale du flux (une seule, hors boucle). `fps_out = frames_out / wall_s`.
- `stages[]` : temps par étage. En `decode` : `demux` + `decode` (+ `upload` en repli logiciel) ; en `vsr-image` : `vsr` mesuré par événements CUDA, plus `upload` / `download` une fois.
- **VRAM (Mio)** : `vram_*` = usage **du processus** par `IDXGIAdapter3::QueryVideoMemoryInfo(…, DXGI_MEMORY_SEGMENT_GROUP_LOCAL).CurrentUsage` (adaptateur choisi par le LUID de `cuDeviceGetLuid`). `vram_rest_mib` = juste avant la création de l'étage (contexte CUDA déjà créé) ; `vram_peak_mib` = maximum échantillonné pendant l'étage ; **`vram_stage_mib = vram_peak_mib − vram_rest_mib` est la valeur comparée aux seuils** (≤ 600 décodage, ≤ 300 VSR), comme au spike. `vram_device_used_peak_mib` = `total − free` de `cuMemGetInfo` (toute la carte, tous processus) : sert au recoupement avec `nvidia-smi`, qui en mode WDDM ne donne pas l'usage par processus. `vram_drift_mib` = `vram_after` de la dernière répétition − celle de la première.
- `process_private_mib` : `GetProcessMemoryInfo` (`PrivateUsage`) au début et à la fin.
- **Aucun chemin complet** dans le JSON (seulement le nom du fichier) : les rapports sont commités dans `docs/qa/` et ne doivent contenir aucune information personnelle.

Point à aligner avec la QA : le protocole § 4.3 prévoit un échantillonnage à 100 ms ; un décodage 720p à ~3 000 i/s d'un clip de 10 s dure ~0,1 s : 100 ms raterait le pic. Défaut proposé **10 ms** (le spike utilisait 5 ms), à reporter dans `protocole.md` par le qa-tester.

## 4. Mesure VRAM in-process

Classe `VramMonitor` (réutilisée par les tests GPU d'ENH-008 et ENH-040) : un thread d'échantillonnage (`std::jthread`, arrêt par `stop_token`) lit DXGI et `cuMemGetInfo` (contexte primaire rendu courant dans ce thread) toutes les `T` ms et garde le maximum en atomique. Sources de mesure derrière une interface `IVramProbe` → testée en CI avec une sonde factice (pic, repos, dérive, arrêt propre).

## 5. Mode `vsr-image` : format d'image

**BMP non compressé** (lecture : 24 bits et 32 bits `BI_RGB` / `BI_BITFIELDS`, de haut en bas ou de bas en haut ; écriture : 24 bits). Pourquoi : s'ouvre directement dans Windows (Photos, Paint), codé en ~150 lignes sans aucune dépendance, testable en CI. Écartés : PNG (zlib / libpng, ou encodeur FFmpeg absent de la build de livraison ENH-048), WIC (COM, plus de code pour peu de gain ici). Une image 4K en BMP pèse ~24 Mo : acceptable pour un contrôle visuel.
Lecture durcie (SEC-13) : en-tête validé, 1 ≤ l, h ≤ 8192, `checked_mul` sur la taille des lignes et de l'image, taille du fichier cohérente ; tests sur en-têtes tronqués ou incohérents.

Démo (sprint-1 § Démo, étape 3) : extraire l'image et produire la référence Lanczos **depuis le même BMP**, pour que la seule différence soit la mise à l'échelle :
```
ffmpeg -i BBB-FAST.mp4 -vf "select=eq(n\,100)" -frames:v 1 -pix_fmt bgr24 image720.bmp
enhance-bench --stage vsr-image --in image720.bmp --out image4k.bmp --q 4 --report vsr.json
ffmpeg -i image720.bmp -vf scale=3840:2160:flags=lanczos -pix_fmt bgr24 lanczos4k.bmp
```
Chemin : BMP → RGB8 en mémoire hôte → `CUarray` ARGB8 → VSR → `CUarray` ARGB8 → BMP. Pas de conversion YUV ici (ENH-042).

### 8.2 Écarts par rapport au plan (à connaître pour lire un rapport)

- **`frames_in` compte la chauffe** (images décodées ou appels VSR, chauffe comprise) pour être comparable à `ffprobe -count_frames` (seuils QA § 4.2) ; `frames_warmup` = la chauffe ; `frames_out` = images chronométrées ; `fps_out = frames_out / wall_s`. Champ ajouté `frames_per_pass` (images d'une passe, = ffprobe, utile avec `--repeat`). Avec `--repeat N`, `frames_*` et `wall_s` sont **cumulés** sur les N passes ; le détail est dans `repeats[]`.
- **Champs ajoutés** : `output`, `vsr_feature` (origine et version de la DLL de fonction VSR, ex. `NgxStoreIdentical 1.6.0`), `vram_io_mib` (images d'entrée / sortie du mode `vsr-image`, hors étage), `vram_device_used_rest_mib` et `vram_device_stage_mib` (recoupement cudaMemGetInfo), `vram_samples`, `warnings[]`, et un `error` structuré `{code, message, detail, native_code}` (le `detail` voit ses dossiers remplacés par `<dir>`).
- **`vram_stage_mib` en `vsr-image`** = pic − repos **après** création des images d'entrée / sortie : c'est la VRAM de l'effet seul, comme le seuil QA d'ENH-040 (≤ 300 Mio). Les images sont dans `vram_io_mib`.
- **`--repeat` existe aussi en `vsr-image`** (le runtime NGX et l'effet sont recréés à chaque passe, un seul runtime vivant à la fois).
- **Repli logiciel** : pas d'étage `upload` séparé ; `decode` inclut la conversion CPU et l'envoi sur le GPU (avertissement dans `warnings[]`).
- **Code 1, deux cas** : (a) arguments invalides, ou `--in` / `--out` / `--report` qui désignent deux fois le même fichier : message sur la sortie d'erreur seulement, **aucun JSON** (le chemin du rapport n'est pas fiable tant que les arguments ne sont pas validés) ; (b) `--out` existe déjà sans `--force` : **JSON avec `error`** (`OutputExists`) si `--report` a pu être ouvert. Les codes 2 à 5 écrivent toujours le JSON avec `error`.
- **Entrée jamais écrasée** (revue cycle 1) : `--in`, `--out` et `--report` sont comparés par identité de fichier (`std::filesystem::equivalent`) quand ils existent, sinon après `weakly_canonical`, sans tenir compte de la casse. `.\a.bmp` contre `a.bmp`, `A.BMP`, `x\..\a.bmp` ou un lien physique sont refusés (code 1), **même avec `--force`**.
- **`--max-frames M`** : arrêt dès que M images sont décodées, donc **au moins M** (les images déjà sorties du dernier paquet sont comptées) ; la valeur exacte est dans `frames_in`.
- **`size_bytes`** vaut 0 si la taille du fichier ne peut pas être lue ; une lecture DXGI en échec ajoute un avertissement dans `warnings[]` (sinon une VRAM à 0 passerait inaperçue).
- **`--decoder nvdec`** : refus (code 2, `UnsupportedFormat`) si FFmpeg / `selectDecoder` ne tente pas NVDEC pour ce flux, ou si le décodeur bascule en logiciel en cours de passe.
- **`git_sha`** : SHA du commit au moment du `configure` CMake (pas de suffixe « modifié »).
- **Sorties transactionnelles** : `OutputFile` supprime le fichier dans son destructeur sauf si `commit()` a été appelé (BMP au succès, rapport après écriture) ; un échec ou une exception ne laisse ni BMP vide ni rapport de 0 octet.
- **Mode 10 bits** : `v10 = round(v8 × 1023 / 255)`, retour `v8 = round(v10 × 255 / 1023)` (aller-retour 8 → 10 → 8 sans perte, testé).

### 8.3 Codes de sortie

| Code | Sens | Erreurs du pipeline |
|---|---|---|
| 0 | succès | — |
| 1 | arguments invalides ou entrée = sortie (sans JSON) ; sortie existante sans `--force` (JSON avec `error`) | `InvalidParams`, `OutputExists` |
| 2 | entrée absente, illisible, corrompue ou non prise en charge | `SourceMissing`, `SourceUnreadable`, `SourceCorrupt`, `UnsupportedFormat` |
| 3 | GPU, pilote ou composant RTX Video absent | `ComponentMissing`, `DeviceLost`, `Busy` |
| 4 | VRAM insuffisante | `OutOfVram` |
| 5 | erreur interne ou écriture impossible | `Internal`, `WriteDenied`, `DiskFull`, `Cancelled` |

**Décodage partiel (QA cycle 2).** En `--stage decode`, une passe est déclarée **abîmée** si au moins un paquet est corrompu (signalé par le démuxeur) ou rejeté par le décodeur (`IDecoder::corruptPackets()`), ou si elle sort moins d'images que le conteneur n'en annonce (`nb_frames`, fichier tronqué ; contrôle désactivé avec `--max-frames`). Par défaut, le banc **refuse la mesure** : code 2, `error.code = "SourceCorrupt"`, `error.detail` = « partial decode: N corrupt or rejected packet(s), F frame(s) of E announced », message sur la sortie d'erreur ; le JSON garde les champs mesurés. Avec `--allow-corrupt`, la mesure est conservée (code 0) mais annoncée dans `warnings[]` et sur la sortie d'erreur. Le JSON porte `corrupt_packets` (cumul des passes) et `frames_expected` (`null` si le conteneur n'annonce rien, ex. certains MKV). Exemples : `gen/edge_corrupt.mp4` 296/300 images, 4 paquets ; `gen/edge_truncated.mp4` 205/300 images, 1 paquet. Les 15 clips valides du corpus et de `in720/` sortent en code 0.

**Répétabilité.** Le seuil de 3 % se calcule sur les `fps_out` de **processus distincts** (une valeur par lancement, médiane par `Measure-Speed.ps1`), pas sur les `repeats[]` d'un même processus, qui sont données à titre indicatif.

### 8.4 Mode d'emploi

L'exécutable est construit par `scripts\build.ps1 -Preset dev` dans `build\dev\src\tools\bench\enhance-bench.exe` (pont RTX Video, `nvngx_vsr.dll` et DLL FFmpeg copiés à côté). `enhance-bench --help` affiche l'aide.

```powershell
$B = "F:\P153\build\dev\src\tools\bench\enhance-bench.exe"
$C = "F:\P153\tests\clips"

# Décodage 720p (NVDEC), rapport JSON
& $B --stage decode --in $C\in720\BBB-FAST.mp4 --report dec.json
# Fuite dans le même processus : 10 passes, dérive dans vram_drift_mib
& $B --stage decode --in $C\in720\BBB-PAN.mp4 --repeat 10 --report rep10.json
# Repli logiciel forcé / NVDEC exigé
& $B --stage decode --in $C\in720\BBB-FAST.mp4 --decoder software --report sw.json
& $B --stage decode --in $C\in720\BBB-FAST.mkv --decoder nvdec      # FFV1 : code 2

# Super-résolution d'une image (démo du sprint) : même BMP pour VSR et Lanczos
ffmpeg -i $C\in720\BBB-FAST.mkv -vf "select=eq(n\,150)" -frames:v 1 -pix_fmt bgr24 in720.bmp
& $B --stage vsr-image --in in720.bmp --out vsr4k.bmp --q 4 --bits 10 --report vsr.json
ffmpeg -i in720.bmp -vf scale=3840:2160:flags=lanczos -pix_fmt bgr24 lanczos4k.bmp

# Script QA (1 chauffe + 5 passes, nvidia-smi en parallèle)
pwsh tests\quality\Measure-Speed.ps1 -Bench $B -Mode Speed -Stage decode -InputFiles $C\in720\BBB-FAST.mp4 `
     -BenchArgs '--repeat 20' -SmiPeriodMs 50 -OutJson speed.json -OutDir $env:TEMP\enh-out
pwsh tests\quality\Measure-Speed.ps1 -Bench $B -Mode Speed -Stage vsr-image -InputFiles in720.bmp `
     -BenchArgs '--bits 10' -SmiPeriodMs 50 -OutJson vsr-speed.json -OutDir $env:TEMP\enh-out
# Mode Leak : -InputFiles attend un TABLEAU ; l'appeler depuis PowerShell (& ...), pas via
# « pwsh -File », qui transmettrait la liste comme une seule chaine.
& .\tests\quality\Measure-Speed.ps1 -Bench $B -Mode Leak -Stage decode `
     -InputFiles @("$C\in720\BBB-FAST.mp4", "$C\gen\core_mp4_h264.mp4", "$C\gen\core_mp4_hevc10.mp4") `
     -OutJson leak.json -OutDir $env:TEMP\enh-out    # liste completee jusqu'a 10 fichiers
```

Pour le recoupement avec `nvidia-smi`, un décodage de 300 images dure ~0,07 s : utiliser `--repeat 20` pour que l'étage dure plus d'une seconde, et `-SmiPeriodMs 50`. Le script compare, **passe par passe** puis en médiane, (pic `nvidia-smi` − repos avant lancement) à la VRAM totale du processus vue par le banc (`vram_peak_mib − vram_process_start_mib`) ; il compare aussi l'étage vu par DXGI (`vram_stage_mib`) et par `cudaMemGetInfo` (`vram_device_stage_mib`).

### 8.7 À retenir en C++

- **RAII « transaction » pour un fichier de sortie** : `OutputFile` supprime le fichier dans son destructeur **sauf** si `commit()` a été appelé au succès ; une exception ou un `return` d'erreur ne laisse donc jamais de sortie incomplète. En C, chaque chemin de sortie devrait penser à `CloseHandle` + `DeleteFile`.
- **`std::jthread` + `stop_token`** : le thread qui échantillonne la VRAM s'arrête et est joint tout seul à la destruction de `VramMonitor`, et `condition_variable_any::wait_for(lock, st, …)` se réveille dès l'arrêt demandé ; en C : `CreateThread`, un drapeau `volatile`, un `WaitForSingleObject` à ne pas oublier.
- **Interface abstraite pour tester sans matériel** : `IVramProbe` a deux implémentations (DXGI/CUDA réelle, factice dans les tests CI) ; l'équivalent C est une structure de pointeurs de fonctions, ici le compilateur vérifie la signature et le destructeur virtuel.
- **`std::cmp_greater` (C++20)** : compare sans piège un entier signé et un non signé (largeur BMP lue en `int32_t` contre une borne `uint32_t`), là où le C convertit silencieusement `-1` en 4 294 967 295.
