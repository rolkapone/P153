# ENH-042 — Conversions couleur CUDA NV12 / P010 <-> RGB : note technique

Statut : note de planning du Sprint 2 (gpu-engineer, 2026-10-29), aucun code. Références : [fiche](../stories/ENH-042.md), [ADR-042](../architecture/ADR-042.md), `src/pipeline/stage/include/enh/pipeline/stage/frame.hpp` (`ColorInfo`, `PlaneView`), `upscaler.hpp` (`RgbFormat`, convention ABGR10 = `x2bgr10le`, R en bits de poids faible), `frame_layout.cpp` (`checkedMul`).

## 1. Approche
- **Une seule source de vérité pour les formules** : `color_math.hpp`, fonctions `__host__ __device__` pures, en **virgule fixe entière** (coefficients x 2^16, `int32`/`int64`, arrondi explicite). Raison : résultats **identiques au bit près** sur CPU et GPU (pas d'écart dû aux FMA de `nvcc`), donc le test CPU de la CI prouve aussi le GPU.
- `resolveColor(ColorInfo, Size)` (fonction pure, CI) applique les règles d'ADR-042 : non étiqueté et <= 576 lignes -> BT.601, sinon BT.709 ; plage limitée sauf `Full`. **BT.2020 / PQ / HLG / Other -> `UnsupportedFormat`** explicite (pas de conversion 709 silencieuse) jusqu'à la story HDR.
- Noyaux (gabarit unique `<YuvFormat, RgbFormat>`) : NV12 -> ARGB8, P010 -> ABGR10, ARGB8 -> NV12, ABGR10 -> P010. Côté YUV : plans linéaires (`PlaneView`, `CUdeviceptr` + pas) ; côté RGB : `CUsurfObject` sur `CUarray` (format imposé par le RTX Video SDK). Les deux croisements (NV12 -> ABGR10, etc.) sortent du gabarit sans coût ; non exposés sauf demande.
- Un fil = un bloc 2x2 de luminance (calcule U/V une fois) ; bords impairs par bornage (clamp) ; tailles et adresses en `std::size_t` via `checkedMul` (SEC-13) ; grille calculée en 64 bits, refus au-delà de 8192x4320.
- **Chrominance** : site « left » (H.264/HEVC par défaut). RGB -> YUV : moyenne du bloc 2x2 aux bons sites. YUV -> RGB : deux modes, `Nearest` (inverse exact) et `Bilinear` (meilleur pour la SR, défaut production). Choix + virgule fixe consignés en **amendement 1 d'ADR-042** avec mesures.
- Sortie toujours BT.709 plage limitée (SDR), étiquetage écrit par l'encodeur (hors périmètre).

## 2. API (interne au pipeline, `src/pipeline/stage/include/enh/pipeline/stage/color.hpp`)
```cpp
struct ResolvedColor { YuvMatrix matrix; bool full_range; };          // Bt601 | Bt709
[[nodiscard]] Result<ResolvedColor> resolveColor(const ColorInfo&, Size) noexcept;
struct YuvImage { PixelFormat format; Size size_px; std::array<PlaneView, 2> planes; };
struct RgbImageRef { RgbFormat format; Size size_px; std::uint64_t surface; }; // CUsurfObject
enum class ChromaUpsample : std::uint8_t { Nearest, Bilinear };
class IColorConverter {            // non copiable, un flux CUDA donné à la création
public:
    virtual ~IColorConverter() = default;
    [[nodiscard]] virtual Result<void> toRgb(const YuvImage&, const RgbImageRef&,
                                             ResolvedColor, ChromaUpsample) noexcept = 0;
    [[nodiscard]] virtual Result<void> toYuv(const RgbImageRef&, const YuvImage&) noexcept = 0;
};
```
- Mise en file sur le flux, **aucune synchronisation ni allocation** (ADR-045) ; paires de formats incohérentes ou tailles différentes -> `UnsupportedFormat` / `InvalidParams` avant tout lancement.
- Implémentations : `CudaColorConverter` (`src/pipeline/gpu/color/`, `.cu`, `sm_120`) ; `CpuColorConverter` (`src/pipeline/core/color/`, référence sur mémoire hôte, même `color_math.hpp`, côté RGB = tampon linéaire hôte) ; utilisée par les tests et par le faux pipeline de la CI.

## 3. Budgets visés (RTX 5070, 4K)
- ABGR10 -> P010 et ARGB8 -> NV12 en 3840x2160 : **<= 0,3 ms** (critère) ; attendu ~0,1 ms (~58 Mo lus + écrits à ~600 Go/s ; ADR-042 mesuré 0,1 ms). NV12/P010 -> RGB en 1280x720 : < 0,05 ms.
- VRAM : **0 Mio alloué par les noyaux** ; tampons fournis par l'appelant (4K : ABGR10 33 Mio + P010 24 Mio). Pic du test 4K <= 100 Mio (hors contexte CUDA), mesuré par `cuMemGetInfo` avant / après.
- Impact sur le débit global : < 1 % du temps d'une image (VSR q4 4K >> 1 ms).

## 4. Tests
**CI sans GPU** (`tests/unit/pipeline/color_*`) :
- coefficients : valeurs connues BT.601/BT.709 (noir, blanc, gris 50 %, primaires, plages limitée et pleine, 8 et 10 bits) ;
- `resolveColor` : table des cas (SD/HD non étiquetés, `Full`, BT.2020/PQ/HLG/Other refusés) ;
- aller-retour sur `CpuColorConverter` avec mire **générée en RGB** (donc dans le gamut) : écart max <= 1/255 (8 bits) et <= 2/1023 (10 bits) en `Nearest` ; écart des moyennes Y/U/V <= 1/1023 ;
- tailles 1x1, 3x3, 1921x1081, 8192x4320 (calcul de géométrie seulement), dépassements refusés (`checkedMul`).
**GPU local** (`tests/gpu/color_test.cpp`, via `scripts/test-gpu.ps1`) :
- **sortie GPU identique au bit près à `CpuColorConverter`** pour les 4 noyaux, les 2 modes, BT.601/709, les deux plages, tailles impaires, 1x1, 8192x4320 ;
- aller-retour sur une image NV12 et P010 décodée par NVDEC (ENH-008, clip de `docs/qa/clips.md`) : critères de la fiche + contrôle `signalstats` (protocole § 2.3) sur la sortie réencodée hors test (QA) ;
- chrono 4K (événements CUDA, médiane de 100 passes, après 10 de chauffe) <= 0,3 ms ; VRAM <= 100 Mio ; 10 fichiers enchaînés sans dérive (> 50 Mio = échec).

## 5. Risques
- **Critère d'aller-retour et `Bilinear`** : l'inverse n'est exact qu'en `Nearest` ; en `Bilinear`, une mire à arêtes de chrominance franches dépasse 1 niveau. Proposé : critère strict en `Nearest` + mire à chrominance lisse en `Bilinear` + critère des moyennes. **À confirmer par qa-tester** (interprétation du mot « mire »).
- Couleurs YUV hors gamut RGB (valides en YUV) : écrêtées, donc aller-retour non réversible ; normal, exclu de la mire.
- Site de chrominance « topleft » (certaines sources HEVC/AV1) non lu par `ColorInfo` : traité comme « left », écart <= 1/4 de pixel de chrominance ; ajout possible (1 champ) si la QA le voit.
- **Rotation / SAR** : ADR-042 les place dans ce noyau, mais ils ne sont pas dans les critères -> hors périmètre ici (idée de story pour le scrum-master).
- NVENC sait prendre de l'ARGB/ABGR10 avec conversion interne, mais sans contrôle documenté de la matrice / plage [H] : on garde nos noyaux.
