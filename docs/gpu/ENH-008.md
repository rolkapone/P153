# ENH-008 — Démuxage FFmpeg et décodage NVDEC : note technique

Statut : note de planning du Sprint 1 (gpu-engineer, 2026-10-21). Aucun code écrit. Références : `docs/gpu/architecture-pipeline.md` (ADR-040, 045, 047, 049, § 3.1-3.5), `docs/gpu/spike.md` § P3.7 (NVDEC mesuré avec `ffmpeg.exe`), `docs/security/threat-model.md` (SEC-08, SEC-13), story ENH-008 de `docs/backlog.md`.
**[H]** = hypothèse à mesurer ; **[M]** = mesuré.

## 1. Approche

- **Démux** : libavformat sur un `AVIOContext` maison (ADR-049). Le fichier est ouvert par `CreateFileW` sur la forme étendue du chemin (`std::filesystem::absolute`, préfixe `\\?\` ou `\\?\UNC\`), `GENERIC_READ`, `FILE_SHARE_READ`, `FILE_FLAG_SEQUENTIAL_SCAN`. Rappels lecture / déplacement (y compris `AVSEEK_SIZE`) sur le `HANDLE`. `avformat_open_input(&ctx, "", nullptr, &opts)` avec `ctx->pb` posé et `AVFMT_FLAG_CUSTOM_IO` (`libavformat/avformat.h` l. 1424). **Aucun chemin texte n'est donné à FFmpeg.**
- **Ouvertures secondaires interdites** : `ctx->io_open` remplacé par un rappel qui renvoie `AVERROR(EPERM)` (l. 1865 ; concerne HLS, `concat`, références externes MOV) ; `protocol_whitelist=file` en défense en profondeur. Option : `format_whitelist` = démuxeurs de la matrice (à aligner avec ENH-048).
- **Décodage** : libavcodec avec hwaccel CUDA (ADR-040). Le contexte matériel FFmpeg **réutilise notre contexte CUDA primaire** : `av_hwdevice_ctx_alloc(AV_HWDEVICE_TYPE_CUDA)`, `AVCUDADeviceContext::cuda_ctx` = notre contexte, `stream` = flux `S_dec`, drapeau `AV_CUDA_USE_PRIMARY_CONTEXT` (`libavutil/hwcontext_cuda.h` l. 63), puis `av_hwdevice_ctx_init`. Rappel `get_format` : choisit `AV_PIX_FMT_CUDA` s'il est proposé, sinon un format logiciel. `extra_hw_frames = 4`.
- **Choix explicite du décodeur natif** : la build BtbN contient `libdav1d`, qui est préféré pour l'AV1 par `avcodec_find_decoder` mais **n'a pas de hwaccel**. On prend donc le décodeur natif par son nom (`av1`, `h264`, `hevc`, `vp9`, `mpeg2video`…) quand NVDEC le gère, et `libdav1d` seulement en repli logiciel. Fonction pure `selectDecoder(codec_id, profil, bits, chroma) → {nom, chemin}` testée en CI.
- **Sortie** : surfaces NV12 (8 bits) ou P010 (10 bits, et 12 bits ramenés à 10) **en mémoire GPU**. Copie GPU→GPU asynchrone (`cuMemcpy2DAsync` sur `S_dec`) de la surface FFmpeg vers notre `DeviceSurfacePool` (8 surfaces pitchées, allouées au démarrage) puis `av_frame_unref` : le pool FFmpeg est libéré tout de suite, la back-pressure se fait sur notre pool. Chaque `VideoFrame` porte un `CudaEvent` (aucune synchronisation CPU dans la boucle, ADR-045).
- **Repli logiciel** (codec ou profil non gérés par NVDEC, ou échec d'init hwaccel) : même `AVCodecContext` sans `hw_device_ctx`, conversion `libswscale` vers NV12 / P010 **directement dans un tampon épinglé** (`cuMemHostAlloc`, 3 tampons tournants), envoi `cuMemcpy2DAsync`. Une ligne de journal (`warn`, code `DecoderFallback`, codec + raison). Les sources 4:2:2 / 4:4:4 sont ramenées en 4:2:0 (perte de chrominance documentée).
- **SEC-13** : `enh::checked_mul` / `checked_add` (`std::size_t`, renvoient `Expected`) ; dimensions bornées dès l'ouverture (1 ≤ l, h ≤ 8192, `av_image_check_size2`), avant toute allocation ; pas de ligne et décalages de plans calculés avec ces fonctions seulement.

## 2. Classes RAII (une ressource C = une classe, `enh::Expected` pour les erreurs)

| Classe | Création → libération | Remarque |
|---|---|---|
| `Win32File` | `CreateFileW` → `CloseHandle` | erreurs Win32 → `SourceMissing` / `SourceUnreadable` (ADR-049) |
| `AvioReader` | `av_malloc` + `avio_alloc_context` → `av_freep(&pb->buffer)` + `avio_context_free` | libère `pb->buffer` (FFmpeg peut l'avoir réalloué), pas le pointeur d'origine |
| `AvInput` | `avformat_alloc_context` + `avformat_open_input` → `avformat_close_input` | détient `AvioReader` et `Win32File` (ordre de destruction par l'ordre des membres) |
| `AvCodecCtx` | `avcodec_alloc_context3` → `avcodec_free_context` | |
| `AvBuffer` | `av_hwdevice_ctx_alloc` / `av_buffer_ref` → `av_buffer_unref` | contexte matériel CUDA |
| `AvPacket`, `AvFrame` | `av_packet_alloc` / `av_frame_alloc` → `av_packet_free` / `av_frame_free` | `std::unique_ptr` + suppresseur |
| `CudaContext`, `CudaStream`, `CudaEvent` | `cuDevicePrimaryCtxRetain` / `cuStreamCreate` / `cuEventCreate` → `Release` / `Destroy` | partagés avec les étages suivants |
| `DeviceSurfacePool`, `PooledSurface` | `cuMemAllocPitch` → `cuMemFree` ; la surface revient au pool dans son destructeur | aucune allocation dans la boucle |
| `PinnedBuffer` | `cuMemHostAlloc` → `cuMemFreeHost` | repli logiciel seulement |
| `SwsCtx` | `sws_getContext` → `sws_freeContext` | repli logiciel |

Tous les codes retour (`int` FFmpeg, `CUresult`, `GetLastError`) passent par `check(...)` → `PipelineError` (code, code natif, `av_strerror` / `cuGetErrorString`, `std::source_location`).

## 3. Interfaces testables sans GPU

Interfaces de `architecture-pipeline.md` § 3.2, créées par cette story : `IDemuxer`, `IDecoder` (`decode(const Packet*, IFrameSink&, std::stop_token)`, `path() → Nvdec | Software`), `IFrameSink`, types `Packet`, `VideoFrame`, `FrameDesc`, `PixelFormat`, `PipelineError`. Faux (CI) : `FakeDemuxer` (paquets synthétiques, erreur injectée à l'image N), `FakeDecoder` (images CPU numérotées), `CollectingSink`.

Découpage CMake proposé (petit écart à ADR-036, à valider avec devops) : `enh_pipeline_ffmpeg` (STATIC, **sans CUDA** : `Win32File`, AVIO, démux, décodage logiciel vers mémoire CPU) compilée en CI dès que FFmpeg est présent ; la partie NVDEC (hwaccel, surfaces CUDA, épinglé) dans `enh_pipeline_gpu`. Prérequis : `enh/expected.hpp` est aujourd'hui dans `src/core/include/` alors que le pipeline ne peut pas dépendre d'`enh_core` (ADR-036, ADR-047) → le déplacer dans `enh_pipeline_api` (ou `enh_common`) au début de la story.

## 4. Matrice des formats

Combinaisons **valides** seulement (WebM n'accepte que VP8 / VP9 / AV1 ; HEVC, VP9, AV1 dans l'AVI ne sont pas standard) : les « 30 combinaisons » du backlog en font ~20.

Corpus généré par script (`tests/gpu/corpus/make-corpus.ps1`, 2 s de `testsrc2` 1280×720, rien de commité) avec l'`ffmpeg.exe` LGPL : `h264_nvenc`, `hevc_nvenc`, `av1_nvenc`, `libvpx-vp9`, `mpeg2video`, `prores_ks` (+ `libopenh264`, `libsvtav1`, `libkvazaar` pour un corpus CI sans GPU).

## 5. Budgets

| Mesure | Budget (story) | Estimation |
|---|---|---|
| Décodage 720p H.264, NVDEC, copie dans notre pool comprise | **≥ 1 000 i/s** | ~3 100 i/s **[M]** avec `ffmpeg.exe -hwaccel cuda` (spike P3.7) ; la copie D2D de 1,4 Mio par image est négligeable |

## 6. Tests

**Unitaires (CI, sans GPU)** : `checked_mul` / bornes (1×1, 8192×4320, 8193, débordement 64 bits) ; `selectDecoder` et choix `get_format` ; `Win32File` (chemin > 260 caractères, accents, espaces, emoji, fichier absent → `SourceMissing`, fichier verrouillé sans partage → `SourceUnreadable`) ; AVIO (lecture, `seek`, `AVSEEK_SIZE`, fin de fichier) ; `io_open` refusé (playlist HLS locale, fichier `concat` et MOV à référence externe pointant vers un autre fichier : erreur propre, aucun autre fichier ouvert) ; décodage **logiciel** du corpus CI (images comptées) ; faux `IDemuxer` / `IDecoder` (ordre, fin de flux, erreur injectée, annulation par `stop_token`). UNC : test exécuté si la variable `ENH_TEST_UNC_DIR` est définie (partage local), ignoré sinon.

**GPU (local, `tests/gpu`, `scripts/test-gpu.ps1`)** : matrice noyau (nombre d'images = `ffprobe`, chemin NVDEC / logiciel attendu, format NV12 / P010) ; vitesse ≥ 1 000 i/s et VRAM ≤ 600 Mio sur `BBB-FAST` (via `enhance-bench --stage decode`, ENH-047, ou en attendant un test GoogleTest chronométré) ; 10 fichiers à la suite, dérive ≤ 50 Mio ; erreur propre sans contexte CUDA (pilote absent simulé par une fabrique qui échoue).

## 7. Risques

| Risque | Parade |
|---|---|
| AV1 décodé par `libdav1d` (CPU) au lieu de NVDEC | décodeur natif choisi par son nom ; test qui vérifie `path() == Nvdec` |
| Profil non géré découvert en cours de flux (changement de résolution, H.264 4:4:4 / 10 bits) | `get_format` rappelé par FFmpeg : bascule logiciel au vol, journalisée ; test dédié dans la matrice reportée |
| Écarts de compte avec `ffprobe` (TS commençant hors image clé, listes d'édition MP4) | comparaison avec la même build FFmpeg ; écarts expliqués au cas par cas |
| Contexte CUDA en double (FFmpeg en créerait un si mal configuré : VRAM et copies inter-contextes) | `AVCUDADeviceContext::cuda_ctx` = notre contexte primaire ; test : un seul contexte (`cuCtxGetCurrent` identique) |
| `nvcuda.dll` / `nvcuvid.dll` chargées par nom par FFmpeg (`ffnvcodec`) | préchargement depuis System32 (SEC-08, ENH-040 / ENH-004) avant toute ouverture |
| Build FFmpeg de livraison (ENH-048) différente de la BtbN de dev | la matrice est rejouée sur la build ENH-048 (critère d'ENH-048) |
| Dérive d'estimation (AVIO + RAII + types de base + matrice) | redécoupage ci-dessous |
