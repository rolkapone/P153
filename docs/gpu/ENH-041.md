# ENH-041 — NGX hors ligne : neutralisation durcie et preuve zéro réseau : note technique

Statut : note de planning du Sprint 2 (gpu-engineer, 2026-10-29), aucun code. Références : [fiche](../stories/ENH-041.md), [ADR-048 + amendement 1](../architecture/ADR-048.md), [findings SEC-30 à SEC-36](../security/threat-model-findings.md), [zero-reseau.md](../security/zero-reseau.md) § 6-8, code ENH-040 : `src/pipeline/rtxvideo/{ngx_guard,ngx_runtime,module_trust,rtxvideo_upscaler}.cpp`, `src/pipeline/rtxvideo_bridge/`.

## 1. Durcissement du code (SEC-30, 31, 32, 35, 36)
- **SEC-30 (échec fermé)** : `ChildProcessBlocker` injecté dans `NgxRuntime` (interface `IChildProcessBlocker`, vrai + faux) ; si `active() == false` juste après sa construction, **aucun appel à `rvb_runtime_create`** : `ComponentMissing{RtxVideoFeatureUntrusted}`, détail `NgxUpdaterNotBlocked`. Même contrôle avant `rvb_vsr_create`. L'avertissement actuel (`ngx_guard.cpp` l. 65, 72 ; `rtxvideo_upscaler.cpp` l. 162) devient une erreur.
- **SEC-31 (contrôle préalable du magasin)** : nouveau `NgxStoreGuard` (RAII), construit avant `rvb_vsr_create` : énumère `%ProgramData%\NVIDIA\NGX\models\vsr\versions\*\files\*` (racine injectable pour les tests), **refuse tout point d'analyse (jonction, lien)**, et applique à chaque fichier la règle PO du 2026-10-24 (identique octet pour octet à notre `nvngx_vsr.dll`, sinon Authenticode hors ligne « NVIDIA Corporation », sinon refus `VsrFeatureUntrusted:`). **Contre la course** : chaque fichier vérifié reste ouvert (`CreateFileW`, `FILE_SHARE_READ` seul) jusqu'à la fin de `rvb_vsr_create`, donc impossible à remplacer ou supprimer pendant la fenêtre ; le contrôle après chargement (ENH-040) est conservé en seconde ligne. Magasin absent ou vide = accepté.
- **SEC-32** : `Pont_AucunCudartImporte_ExportsAttendus` compare l'ensemble **exact** des exports : 7 `rvb_*` + les 27 `NVSDK_NGX_*` listés dans SEC-32 (34 noms, liste figée dans le test).
- **SEC-35** : le pont ne lie plus `CUDA::cuda_driver` (`rtxvideo_bridge/CMakeLists.txt` l. 20) ; table RAII `DriverApi` chargée une fois par `LoadLibraryExW(L"nvcuda.dll", nullptr, LOAD_LIBRARY_SEARCH_SYSTEM32)` + `GetProcAddress` des **10** fonctions utilisées (`cuInit`, `cuDeviceGet`, `cuDeviceGetAttribute`, `cuDeviceGetName`, `cuDeviceGetLuid`, `cuCtxGetDevice`, et les noms versionnés `cuDeviceTotalMem_v2`, `cuCtxPushCurrent_v2`, `cuCtxPopCurrent_v2`, `cuDeviceGetUuid_v2` : `cuda.h` CUDA 13.4 l. 89, 140-141, 155). Symbole absent -> `ComponentMissing{Driver}`. Lu : aucune référence `cu[A-Z]*` dans `nvsdk_ngx_s.lib` x64 (seulement `cudart`, déjà couvert par `cudart_shim.cpp`). Effet de bord : `cuda.lib` n'est plus incorporé, la question de licence SEC-35 (a) disparaît.
- **SEC-36** : `docs/gpu/ENH-040.md` § 4 renvoyé au § 10 et à ADR-048 amendement 1, l. 88 corrigée (34 exports, pas d'énumération des modules).
- Rien ne change pour `NVSDK_NGX_UpdateFeature` (déjà interdit par C1 + `ngx_static_policy_test`), `AppId = 0`, `InApplicationDataPath`.

## 2. API
Pas de nouvelle API publique. Nouveau détail d'erreur `NgxStoreUntrusted:` (préfixe `VsrFeatureUntrusted:` conservé pour l'interface), `NgxUpdaterNotBlocked`. Signature interne : `NgxRuntime::create(BridgeApi&, std::unique_ptr<IChildProcessBlocker>(*)(), const NgxStorePolicy&)`.

## 3. Budgets
VRAM : **0 Mio** de plus. Débit : aucun effet (hors boucle chaude). Initialisation : + **<= 300 ms** (taille + SHA-256 de quelques fichiers du magasin, Authenticode hors ligne), mesuré par `enhance-bench --stage vsr-image` avant / après.

## 4. Preuve zéro réseau (M1-M3), `scripts/test-no-network-dynamic.ps1`
**Aucun outil à télécharger** : `New-NetFirewallRule`, `auditpol`, `Get-WinEvent`, `wevtutil`, `pktmon`, `Get-NetTCPConnection` sont intégrés à Windows 11. Processus visés : `enhance-bench.exe` et `enh_gpu_rtxvideo_tests.exe` (seuls à initialiser NGX aujourd'hui ; `Enhance.exe` sera ajouté à ENH-009, paramètre `-Program`). Scénario : magasin `InApplicationDataPath` vidé, 3 initialisations NGX + VSR 720p -> 4K q4, puis tests `ENH040.*`.
- **M1 pare-feu bloquant** : règles entrée / sortie `Block` sur les exécutables visés ; échantillonnage 250 ms des points TCP/UDP par PID ; critère : 0 point, durée d'init comparable à une passe sans règle (pas d'attente de 15-30 s), sorties identiques (SHA-256).
- **M2 audit WFP** : `auditpol` « Filtering Platform Connection » (état d'origine restauré), événements 5156-5159 lus **pour tous les processus**, fenêtre de test comparée à 60 s de repos. Critère : 0 événement des processus visés ; tout événement nouveau d'un processus NVIDIA (`nvngx_update.exe`, `NVDisplay.Container.exe`, `NVIDIA app`) = **télémétrie déléguée (R-8)** -> rapport secdevops. Couvre SEC-34 (pas de 5157 pendant `WinVerifyTrust`).
- **M3 capture** : passe réseau actif sans règle ; `pktmon start --capture --comp nics --pkt-size 0` 60 s au repos puis 60 s de test, `pktmon etl2txt` (pas besoin de Wireshark), journal `Microsoft-Windows-DNS-Client/Operational` activé le temps du test (requêtes DNS avec PID) ; diff des destinations. Plus : instantané (chemin, taille, SHA-256) de `%ProgramData%\NVIDIA\NGX\` et du dossier de données avant / après (aucun fichier nouveau), provenance des modules (C5).
- Droits administrateur obligatoires, `finally` qui restaure tout. **Exécution par le PO** (PowerShell en administrateur, une commande ; aucune frappe simulée par un agent, décision n° 19). Bruts dans `build/zero-net/` (non versionné), synthèse <= 60 lignes dans `docs/security/ENH-041-zero-reseau.md`. Trafic CRL/OCSP -> exception documentée ou PO ; **téléchargement de DLL par NGX -> escalade immédiate au PO**.
- Seulement si anomalie à analyser : demander au PO Wireshark (wireshark.org, outil d'analyse, non livré) ou Process Monitor (Sysinternals, learn.microsoft.com).

## 5. Tests
**CI sans GPU** : faux bloqueur inactif -> refus et 0 appel `rvb_runtime_create` (`FakeBridgeApi`) ; `NgxStoreGuard` sur arborescence temporaire : vide, copie identique, signé NVIDIA (fichier fourni par un faux `ITrustVerifier`), non signé, jonction, fichier illisible -> verdicts attendus ; `DriverApi` avec faux `GetProcAddress` (symbole manquant) ; contrôle statique : pas de `CUDA::cuda_driver` dans le pont, `LoadLibraryExW("nvcuda.dll"` toujours avec `LOAD_LIBRARY_SEARCH_SYSTEM32`.
**GPU local** (`scripts/test-gpu.ps1`) : 34 exports exacts, aucun import `nvcuda.dll` / `cudart*` dans le pont ; `nvcuda.dll` chargée depuis System32 ; magasin réel lu sans refus à tort ; pendant l'init, une ouverture en écriture d'un fichier du magasin échoue (partage) ; 10 cycles sans dérive VRAM ; tests ENH-040 toujours verts.

## 6. Risques
- Nomenclature : la fiche nomme M1 pare-feu / M2 audit / M3 capture, `zero-reseau.md` § 8 nomme M1 hors ligne / M2 capture / M3 origine DLL. **Retenu ici : celle de la fiche** ; le test « mode avion » (§ 8 M1) reste à ENH-001. À aligner (secdevops).
- La fiche dit « journalisation NGX désactivée en release » : faux depuis ENH-040 (journal au niveau ON gardé en mémoire, jamais écrit, nécessaire au contrôle). Critère à reformuler : « aucun fichier journal NGX écrit » (scrum-master).
- NGX peut ouvrir un fichier du magasin en écriture : notre verrou ferait échouer `rvb_vsr_create` [H] ; repli : verrou retiré, contrôle préalable + après chargement seulement.
- Fichiers `.bin` du magasin : Authenticode reconnu malgré l'extension [H] (à vérifier sur la copie déjà présente) ; refus d'un fichier non signé non utilisé = échec fermé voulu, message clair.
- Télémétrie déléguée à un service du pilote : hors de notre contrôle ; on mesure et on documente (R-8), pas de modification du registre (ADR-048).
