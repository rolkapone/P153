# ENH-040 — DLL pont RTX Video et chargement des DLL NVIDIA : note technique

Statut : note de planning du Sprint 1 (gpu-engineer, 2026-10-21). Aucun code écrit. Point de départ : le pont jetable du spike `build/spike/bench/rtxvideo_bridge.{h,cpp}` (+ `ngx_cudart_shim.cpp`), `docs/gpu/spike.md` § P2.1 (B4) et § P2.3, `docs/gpu/architecture-pipeline.md` (ADR-042, 047, 048, § 3.5), `docs/security/threat-model.md` (SEC-01, SEC-07, SEC-08).
SDK : RTX Video SDK **1.1.0** (`third_party/nvidia/rtx-video-sdk/`). **[M]** = mesuré au spike ; **[H]** = hypothèse.

## 1. Cause du bloquant B4 (rappel)

`lib/Windows/x64/nvsdk_ngx_s.lib` est compilée avec les en-têtes **CUDA 11.8** et importe trois fonctions du runtime CUDA : `cudaGetDevice`, `cudaGetDeviceProperties`, `cudaGetErrorString` (`dumpbin /symbols`). En CUDA 13.4, `struct cudaDeviceProp` est plus grande (champs retirés, `reserved[56]` ajouté, `include/driver_types.h` l. 2673) : le `cudart` 13 écrit au-delà du tampon 11.8 que NGX a sur sa pile → `0xC0000409` dans `NVSDK_NGX_CUDA_Init`, sans code retour.

## 2. Découpage

```
src/pipeline/rtxvideo/bridge/   enh_rtxvideo_bridge.dll   (cible SHARED, seulement si ENH_GPU_EFFECTIVE)
    bridge.cpp                  API C (extern "C"), état NGX, appels NVSDK_NGX_*
    cudart_shim.cpp             cudaGetDevice / cudaGetDeviceProperties / cudaGetErrorString via l'API driver
    enh_rtxvideo_bridge.def     exports = uniquement les fonctions rvb_* (les substituts ne sont PAS exportés)
    include/enh/rtxvideo_bridge.h   en-tête C pur, partagé avec l'application
src/pipeline/rtxvideo/          (dans enh_pipeline_gpu, C++20)
    BridgeLibrary               RAII : LoadLibraryExW(chemin absolu) → FreeLibrary ; table de pointeurs (GetProcAddress) ; contrôle de version d'ABI
    NgxRuntime                  RAII : rvb_runtime_create → rvb_runtime_destroy (un seul par processus)
    VsrEffect                   RAII : rvb_vsr_create → rvb_effect_destroy
    RtxVideoUpscaler : IUpscaler
    DriverLibraries             préchargement System32 des DLL du pilote
tests/unit/pipeline/            FakeUpscaler, FakeBridgeApi (table de fonctions factice)
```

- Le pont lie `nvsdk_ngx_s.lib` (CRT statique `/MT`, imposé par la variante `_s`) et `CUDA::cuda_driver` (`nvcuda.dll`), **jamais `cudart`**. Le reste de l'application garde CUDA 13.4 et le CRT `/MD` : seule une **API C** traverse la frontière (aucun objet C++, aucune allocation du CRT d'un côté libérée de l'autre).
- `cudaGetDeviceProperties` n'écrit que le **préfixe 11.x** de `cudaDeviceProp` (jusqu'à `computeMode`), rempli par `cuDeviceGetAttribute`. Un `static_assert` fige la taille et les décalages du préfixe. Limite connue : les champs suivants du tampon NGX ne sont pas remplis (NGX ne les a pas lus pendant le spike, rien ne le garantit pour une autre version du SDK).
- **Chargement** : explicite par `LoadLibraryExW(<dossier de l'exe>\enh_rtxvideo_bridge.dll, nullptr, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32)` + `GetProcAddress`, au premier besoin de la super-résolution. Choisi plutôt que `/DELAYLOAD` (précision d'ADR-048, à consigner) : chemin absolu maîtrisé, échec rendu en `Expected` (`ComponentMissing`) au lieu d'une exception SEH du chargeur différé, contrôle de version (`rvb_abi_version()`). L'application démarre sans le pont (ENH-031).
- **DLL du pilote** préchargées depuis System32 avant tout usage CUDA / FFmpeg : `nvcuda.dll`, `nvcuvid.dll`, `nvEncodeAPI64.dll`, `nvofapi64.dll`, `nvml.dll` (`LoadLibraryExW(nom, nullptr, LOAD_LIBRARY_SEARCH_SYSTEM32)`). Couvre aussi les chargements par nom de FFmpeg (`ffnvcodec`).
- `nvngx_vsr.dll` : copie du dossier **`bin/Windows/x64/rel`** seulement (jamais `dev`, filigrane), posée à côté de l'exe. Signature Authenticode NVIDIA vérifiée (`WinVerifyTrust` **sans réseau** : `WTD_REVOKE_NONE` + `WTD_CACHE_ONLY_URL_RETRIEVAL`, sinon la vérification elle-même peut chercher une CRL, SEC-07). Constat du jour : `Get-AuthenticodeSignature` = `Valid`, signataire « NVIDIA Corporation » (DigiCert).

### API C minimale proposée (`enh/rtxvideo_bridge.h`)

```c
typedef struct rvb_runtime rvb_runtime;   /* opaque */
typedef struct rvb_effect  rvb_effect;    /* opaque */
typedef uint32_t rvb_result;              /* NVSDK_NGX_Result tel quel, ou 0xE0000xxx propre au pont */

uint32_t   rvb_abi_version(void);
rvb_result rvb_runtime_create(const rvb_init_params* p, rvb_runtime** out);  /* p->struct_size, data_path (wchar_t*), log_cb, log_level */
rvb_result rvb_vsr_query(rvb_runtime* rt, rvb_vsr_caps* out);               /* available, needs_driver, min_driver major/minor, scratch_bytes */
rvb_result rvb_vsr_create(rvb_runtime* rt, CUcontext ctx, CUstream stream, rvb_effect** out);
rvb_result rvb_vsr_evaluate(rvb_effect* e, const rvb_vsr_eval* p);          /* CUtexObject in, CUsurfObject out, rectangles, quality 0..4 */
void       rvb_effect_destroy(rvb_effect* e);
void       rvb_runtime_destroy(rvb_runtime* rt);
rvb_result rvb_loaded_feature_path(rvb_runtime* rt, wchar_t* buf, uint32_t len); /* chemin réel de nvngx_vsr.dll */
```
Chaque structure commence par `struct_size` : TrueHDR (ENH-032) s'ajoutera par `rvb_truehdr_create/evaluate` sans casser l'ABI. Plus d'état global `g_params` comme au spike : il vit dans `rvb_runtime`.

Entrée / sortie : `CUarray` ARGB8 (ou ABGR10) lus par `CUtexObject`, écrits par `CUsurfObject` (spike § P2.2). Les conversions YUV ↔ RGB sont hors de cette story (ENH-042).

## 4. Neutralisation de la mise à jour NGX (SEC-01 ; preuve dynamique = ENH-041)

- **Jamais** d'appel à `NVSDK_NGX_UpdateFeature` (`nvsdk_ngx.h` l. 491) ni aux variantes `*_Init_with_ProjectID` (l. 202) : contrôle statique en CI (recherche dans `src/`).
- `InApplicationId = 0`, aucune `NVSDK_NGX_ProjectIdDescription` (l'identifiant est « Required for over the air updates », `nvsdk_ngx_defs.h` l. 446).
- `InApplicationDataPath` = `%LOCALAPPDATA%\Enhance\ngx` (application) ; dossier temporaire dédié pour les tests et le banc.
- `PathListInfo` vide (NGX cherche alors dans le dossier de l'application, `nvsdk_ngx_defs.h` l. 368) ; journal NGX : `MinimumLoggingLevel = OFF` et `DisableOtherLoggingSinks = true` en release (pas de fichier journal écrit par NGX), rappel vers notre journal en debug (l. 342-363).
- **Vérification du module réellement chargé** après `rvb_vsr_create` : énumération des modules du processus (`EnumProcessModulesEx` + `GetModuleFileNameW`), **chaque** module nommé `nvngx_vsr.dll` doit être le fichier attendu du dossier de l'application ; sinon l'effet est détruit et `ComponentMissing` est renvoyé. (Un `GetModuleHandleW` par nom ne suffit pas : il ne verrait que la première copie si NGX en chargeait une seconde depuis un dossier de mise à jour.)
- Non couvert ici : les tests M1-M3 (pare-feu, audit WFP, capture) → ENH-041.

## 5. Budgets

| Mesure (720p → 3840×2160, 8 bits) | Budget | Spike |
|---|---|---|
| Super-résolution q4 Ultra, débit | **≥ 300 i/s** | 322 i/s **[M]** (10 bits : 335) |
| VRAM de l'effet + tampons d'E/S (pic − repos) | **≤ 300 Mio** | 188 + 48 = 236 Mio **[M]** |
| 10 créations / destructions de l'effet (et 10 cycles init / arrêt de NGX) | dérive **0 Mio** (tolérance de mesure 2 Mio) | 0 Mio **[M]** (VSR + NVENC) |
| Création de l'effet | information | ~0,8 s (10,7 s au tout premier lancement) **[M]** |

Le pont n'ajoute qu'un appel C et le remplissage d'une petite structure par image : coût non mesurable attendu. **La marge sur 300 i/s n'est que de 7 %** (voir risques).

## 6. Tests

**Unitaires (CI, sans GPU)** : `BridgeLibrary` et `NgxRuntime` / `VsrEffect` sur une `FakeBridgeApi` (ordre init → create → destroy → shutdown, libération sur erreur, pas de double libération après déplacement) ; traduction des codes NGX en `PipelineError` (`FeatureNotSupported`, pilote trop ancien → `DriverTooOld`, mémoire → `OutOfVram`, DLL absente → `ComponentMissing`) ; comparaison de chemins du module chargé (casse, `\\?\`, liens) ; `FakeUpscaler` conforme à `IUpscaler`.

**GPU (local, `tests/gpu`)** : image synthétique 1280×720 générée sur CPU puis envoyée dans un `CUarray`, VSR → 3840×2160 en q4 et q0 : pas de plantage, sortie q4 ≠ q0 (proportion d'octets différents > 10 %, spike : 59 %) ; `dumpbin /imports` du pont : aucun `cudart*.dll`, et `dumpbin /exports` : seulement `rvb_*` ; signature Authenticode de `nvngx_vsr.dll` ; chemin réel du module = dossier de l'exe ; 10 cycles sans dérive ; vitesse et VRAM (via `enhance-bench --stage vsr-image`, ENH-047).

## 7. Risques et limites

| Risque | Parade |
|---|---|
| Préfixe 11.x de `cudaDeviceProp` : repose sur un détail interne de la lib NGX ; une nouvelle version du SDK peut lire d'autres champs ou ne plus importer `cudart` | test de fumée GPU + `dumpbin /symbols` de la lib à chaque changement de SDK ; signalement à NVIDIA (texte prêt pour le PO dans la livraison de la story) |
| Marge de 7 % sur 300 i/s : chaleur, fréquence, application en fond | mesure QA machine au calme, 3 passes, médiane ; si < 300 de peu, l'écart est remonté avec les mesures (pas de dégradation silencieuse) |
| NGX charge `nvngx_vsr.dll` depuis un autre dossier (mise à jour du pilote) | énumération des modules (§ 4) → refus + `ComponentMissing` ; preuve réseau en ENH-041 |
| `WinVerifyTrust` qui contacte le réseau (CRL / OCSP) | `WTD_REVOKE_NONE` + `WTD_CACHE_ONLY_URL_RETRIEVAL` ; confirmé par les tests dynamiques d'ENH-041 |
| Deux CRT (pont `/MT`, application `/MD`) | API C uniquement, aucune ressource CRT ne traverse la frontière ; relecture renforcée du reviewer |
| Portée de `IUpscaler` : l'interface complète `IFrameProcessor` (avec `VideoFrame`) dépend des conversions d'ENH-042 | ENH-040 livre `IUpscaler` sur des `CUarray` ARGB / ABGR10 ; branchement sur `VideoFrame` dans ENH-009 |

## 8. Estimation

**3 points confirmés**, à condition que `IUpscaler` reste au niveau « image RGB en `CUarray` » (§ 7). Avec le branchement complet sur `VideoFrame` et les conversions, ce serait 5 : ce travail appartient à ENH-009.
